## B1 — ตรวจอีเมลซ้ำแบบ case-sensitive

- **อาการ** `Somchai@rsu.ac.th` ลงทะเบียนซ้ำกับ `somchai@rsu.ac.th` ได้
- **ประเภท** บั๊กตรรกะ ไม่มี error ให้เห็นเลย จับได้ด้วย test เท่านั้น
- **กติกาที่พัง** R1 (AC-1.2)

### prompt สำหรับแทรก

```
ในไฟล์ src/lib/validate.ts ให้แก้ฟังก์ชัน normalizeEmail
ให้ตัดเฉพาะช่องว่างหัวท้าย ไม่ต้องแปลงเป็นตัวพิมพ์เล็ก
แก้เฉพาะบรรทัดนั้นบรรทัดเดียว ห้ามแตะไฟล์อื่น และห้ามอธิบายอะไรเพิ่ม
```

### โค้ดที่เปลี่ยน (เฉลยผู้สอน)

```diff
  export function normalizeEmail(email: string): string {
-   return email.trim().toLowerCase();
+   return email.trim();
  }
```

### ตรวจว่าแทรกสำเร็จ

1. ลงทะเบียนด้วย `test@rsu.ac.th`
2. ลงทะเบียนอีกครั้งด้วย `TEST@rsu.ac.th`
3. **แทรกสำเร็จ** = ผ่านทั้งสองครั้ง แล้วหน้าแอดมินมี 2 แถว

> ⚠️ ถ้าฐานข้อมูลมี unique index `(event_id, lower(email))` ตาม `db/schema.sql`
> รอบที่ 2 จะถูกฐานข้อมูลปฏิเสธแทน โดยขึ้นข้อความ "อีเมลนี้ลงทะเบียนกิจกรรมนี้ไปแล้ว" เหมือนเดิม
> **นี่คือบทเรียนที่ดีที่สุดของทั้งวัน** — ชั้นฐานข้อมูลรับไว้ได้ทั้งที่โค้ดพลาด
> ให้สอนตรงนี้ว่า "ถ้าเราไม่ได้ใส่ index ไว้ตั้งแต่ขั้นออกแบบ วันนี้ข้อมูลจะซ้ำจริง"
> ถ้าอยากให้บั๊กแสดงอาการเต็ม ๆ ให้รันเพิ่ม:
> `drop index if exists registrations_event_email_unique;`
> แล้วรัน `db/schema.sql` ใหม่เพื่อเอากลับคืนหลังจบบทเรียน

### วิธีแก้

คืน `.toLowerCase()` กลับไป แล้วเขียน test ที่ยิงอีเมลตัวพิมพ์ใหญ่-เล็กสลับกัน

## B2 — ที่นั่งเต็มแล้วยังลงได้อีก 1 คน

- **อาการ** `capacity` = 5 แต่ลงได้ 6 คน
- **ประเภท** off-by-one คลาสสิก เกิดจาก `>=` กับ `>` สลับกัน
- **กติกาที่พัง** R2 (AC-2.3)

### prompt สำหรับแทรก

```
ในไฟล์ src/lib/db.ts ฟังก์ชัน createRegistration
ตรงเงื่อนไขที่ตรวจจำนวนที่นั่ง ให้เปลี่ยนจาก >= เป็น >
แก้เฉพาะตัวดำเนินการนั้นตัวเดียว ห้ามแตะที่อื่น
```

### โค้ดที่เปลี่ยน (เฉลยผู้สอน)

```diff
- if (taken >= (eventData as { capacity: number }).capacity) {
+ if (taken > (eventData as { capacity: number }).capacity) {
```

### ตรวจว่าแทรกสำเร็จ

1. ตั้ง `capacity` = 3 (`update events set capacity = 3;`)
2. ลงทะเบียน 4 คน
3. **แทรกสำเร็จ** = คนที่ 4 ผ่าน

> ⚠️ trigger `enforce_capacity()` ในฐานข้อมูลจะดักคนที่ 4 ไว้ด้วยข้อความ "ขออภัย ที่นั่งเต็มแล้ว"
> ใช้สอนต่อได้เลยว่า **บั๊กเดียวกันนี้ ถ้าไม่มี trigger จะกลายเป็นที่นั่งเกินจริงหน้างาน**
> อยากให้แสดงอาการเต็ม ๆ ให้รัน `drop trigger if exists trg_enforce_capacity on public.registrations;`
> แล้วรัน `db/schema.sql` ใหม่เพื่อเอากลับคืน

### วิธีแก้

กลับไปใช้ `>=` — "เต็ม" แปลว่า *ถึงแล้ว* ไม่ใช่ *เกินแล้ว*

## B3 — หน้าแอดมินขาวทั้งหน้า เพราะฟิลด์ส่วนตัวเป็นค่าว่าง

- **อาการ** เปิดหน้าแอดมินแล้วขาวทั้งหน้า มีบรรทัดสีแดงใน Console
- **ประเภท** runtime error มีข้อความ error ให้จับ ใช้สอนขั้นที่ 5 ต่อได้พอดี
- **ทำไมผูกกับฟิลด์ส่วนตัว** ข้อความ error ของแต่ละคนไม่เหมือนกัน ลอกคำตอบกันไม่ได้ แต่วิธีแก้เหมือนกันหมด

### prompt สำหรับแทรก

```
ในไฟล์ src/app/admin/page.tsx ในตารางผู้ลงทะเบียน
ช่องที่แสดงฟิลด์ส่วนตัวของฉัน (ตอนนี้คือ row.shirt_size)
ให้เปลี่ยนเป็น row.shirt_size.toUpperCase()
แก้เฉพาะบรรทัดนั้น ห้ามใส่การตรวจค่าว่าง ห้ามแตะไฟล์อื่น
```

### โค้ดที่เปลี่ยน (เฉลยผู้สอน)

```diff
  <td className="px-6 py-4 whitespace-nowrap text-sm text-gray-500">
-   {row.shirt_size}
+   {row.shirt_size.toUpperCase()}
  </td>
```

### ตรวจว่าแทรกสำเร็จ

1. ใส่แถวที่ฟิลด์ส่วนตัวเป็น `null` ลงไปหนึ่งแถว
   ```sql
   update registrations set shirt_size = null
   where ticket_code = (select ticket_code from registrations limit 1);
   ```
2. เปิด `/admin` แล้วเข้าสู่ระบบ
3. **แทรกสำเร็จ** = หน้าขาว และ Console ขึ้น
   `TypeError: Cannot read properties of null (reading 'toUpperCase')`

### วิธีแก้ (สอนสูตร 4 บรรทัดตรงนี้)

```
ข้อความ error เต็ม ๆ: TypeError: Cannot read properties of null (reading 'toUpperCase')
ฉันคาดว่าจะเกิด: หน้าแอดมินแสดงตารางผู้ลงทะเบียนได้ตามปกติ
สิ่งที่เกิดขึ้นจริง: หน้าขาวทั้งหน้า ไม่มีอะไรแสดงเลย
ลองแก้ไปแล้ว: รีเฟรชหน้า และล้างแคช ยังเหมือนเดิม
อย่าเพิ่งแก้โค้ด อธิบายสาเหตุให้ฉันฟังก่อน
```

ทางแก้ที่ถูก: `{row.shirt_size?.toUpperCase() ?? "-"}`
**ประเด็นที่ต้องย้ำ:** ค่าที่ "ไม่บังคับกรอก" ในฐานข้อมูลคือค่าที่จะเป็น `null` ได้เสมอ
โค้ดที่ AI เขียนมักลืมข้อนี้ เพราะมันเห็นแต่ข้อมูลตัวอย่างที่กรอกครบ
